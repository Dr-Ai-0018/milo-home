# 备份与恢复

备份位置、仓库、凭据和保留政策由部署者配置；项目不假定某个restic仓库或宿主脚本存在，也不自动安装每日备份timer。先明确资料分类和预算，再接到自己的备份系统。维护摘要区分每日任务、完整配套采集、准确远端取回和独立恢复，不能互相代签。

## 基础数据库备份

使用同一应用配置，输出到源码和Web根外的新私密文件；父目录0700、文件0600，目标不能已存在：

```sh
milo-home --config /etc/milo-home/site.toml backup --out /var/backups/milo-home/NEW/database.sqlite3
milo-home --config /etc/milo-home/site.toml backup-rehearse \
  --file /var/backups/milo-home/NEW/database.sqlite3 \
  --out /var/backups/milo-home/NEW/rehearsed.sqlite3
```

路径均为示例，先创建实际的新私密父目录。按数据库属主执行或沿支持的服务账号管理入口；不要改变原库属主来方便备份。应用采用SQLite在线备份，不把并发复制的DB/WAL当成一致快照。演练在新文件迁移／重开，核对完整性与逻辑记录，不接入执行器、不覆盖原库。

## 完整资料与远端

启用交办／持久对话后，数据库单件不等于完整恢复包。按[维护采集流程](maintenance.md)保存同代业务库、journal、原生对话／冷热段、映射、工作区成果、附件、公开资产、分类与版本。include/exclude须覆盖新文件和真实根；临时凭据、`auth.json`和运行交付的秘密不进入公开材料或普通归档。长存密钥与恢复凭据独立加密保管。

每日在线备份可沿现有系统接入，显式纳入所有实际根与配置引用；维护摘要目录通常独立，不能只备数据根就宣称覆盖。每日成功标记和service退出码只能证明各自事实。TOML中`maintenance.daily_unit`与`success_file`均省略时如实未知，不默认接某台机器的备份工具。

远端验证使用准确快照ID和可信manifest，取到新私密目录，比对长度和SHA-256后独立恢复；不把任意latest、目录列举或服务成功当作恢复成功。恢复窗口之外再上传／取回，不为了验证重复执行全机备份。保持现有保留规则，删除代次或远端prune需独立决策。

## 实际恢复

1. 选定兼容该schema的代码与准确同代材料，在独立目录验摘要、权限、完整性和业务关系。
2. 停止新领并核对原进程家族确已停止，保存原数据和服务状态；未知占用继续保留，不能在两份库同时启动执行器。
3. 明确唯一数据路径、原生主身份及回退方案，恢复服务账号与0700/0600权限后，先检查API／鉴权／内容和下载。
4. 文件恢复不自动授权恢复执行。跨inode／跨机器须按原绑定恢复规则另行核验并重新登记，再逐一恢复本次暂停入口。

程序没有自动覆盖生产库的命令。配置加载方式或代码目录改变，不应重建主对话、重算指纹、清失败账本或覆盖原策略。升级后的新库不能直接换回旧快照而丢弃新写入。
